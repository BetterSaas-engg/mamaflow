| D39 | Extraction cost controls: bounded retries + per-user daily call budget + no schema in the prompt | active | 2026-07-27: 3 test users cost ~$2.40 USD/day (~$24/user/month) — fatal for a free ad-supported product (ad revenue ≈ $0.30–1.50/user/mo). Root cause was NOT model or email size: `sync_runner` wrote the `synced_messages` marker only after a SUCCESSFUL extraction while a bare `except Exception` swallowed every failure with no counter, so a permanently-failing message was re-sent hourly for up to 30 days (~720 full-price calls). Measured ~216 calls/user/day vs an inbox nowhere near that. Fixes: (a) bounded retries — `attempts`/`failure_kind` on `synced_messages`, typed taxonomy (400/422 permanent → give up at once; 429/5xx/DB transient → max 3 tries; 401/403 fatal → abort the run so a bad key can't burn the batch), circuit breaker at 5 consecutive transient failures; (b) per-user daily call budget (200, `extraction_usage` table) as the structural backstop against the NEXT unforeseen runaway; (c) deleted the inline JSON-schema dump from the prompt — it was already sent as the tool's `input_schema` with `strict: True`, so the prose copy cost ~587 tok/call (25% of input) for nothing; A/B on 5 real-shaped cases (D37 invite, multi-event newsletter, dateless action, relative date, no-signal) gave identical items and identical dates; (d) `message.usage` is now captured and logged per sync (counts + model id only — the model id makes an accidental EXTRACTION_MODEL flip attributable from one grep). Expected: ~$24 → ~$2.82/user/month typical. **Deliberately NOT done**: prompt caching (nonce kills the prefix match and Haiku's 4096-token minimum is above our whole scaffolding), lowering `max_tokens` (a ceiling, not a charge — $0 saved). Deferred with a PM-agreed quality bar: body trimming + gate tightening must be corpus-gated with CI-enforced 100% recall on a must-pass set (a missed event costs trust; a false pass costs $0.0025), and the Batch API (−50%) for hourly auto-sync only, keeping interactive sync realtime. |

| D40 | Sync window = **wide scan (500) + bounded run (50), oldest-first, with every terminal verdict marked** | active | 2026-07-28. `_list_recent_ids` returned one un-paginated page of the newest 50 of the 30-day window, so once those synced, everything older was never listed again and could never be extracted — silently. Worst case is a NEW user: a 30-day backlog of hundreds, of which only the newest 50 ever process. Fix splits the reader contract into `list_recent_ids` (ids only, paginated to `SYNC_SCAN_MAX_MESSAGES=500`) + `fetch_metadata` (headers for given ids), so the runner dedups on **ids before fetching any headers** — a quiet inbox now costs one list call instead of re-reading the whole window hourly. The run stays bounded at `SYNC_MAX_MESSAGES_PER_RUN=50`, processed **oldest-first** so a backlog drains in arrival order, with the remainder logged as queued rather than dropped. **Security audit of the first commit found the fix re-created the bug through a different door** (confirmed by simulation, not inspection): blocked senders were never marked, so they stayed "unsynced" for the whole window and — under oldest-first selection — permanently saturated every batch once in-window blocked volume exceeded the per-run cap, which the seed blocklist (linkedin/amazon/shopify/etsy) makes ordinary. Blocked ids are now retired via `mark_messages_blocked` into the same marker table as successes: both are terminal verdicts, and no body was fetched so no content is stored. Trade-off accepted: a later blocklist change does not reconsider already-classified mail (same shape as the D36 gate; the blocklist is structural, not a user knob). IMAP needed one more fix — a message id IS a header there, so `list_recent_ids` and `fetch_metadata` were each scanning the full window; they now share one scan via a single-use, TTL'd handoff (falls back to a fresh scan, so it can never serve stale mail). **Known bound, deliberately not raised here:** mail beyond position 500 in the 30-day window is still never listed — fine below ~16 emails/day, not above; raising `SYNC_SCAN_MAX_MESSAGES` costs only cheap Gmail list calls (Claude spend stays capped by the per-run bound) but widens the dedup `IN` clause, so it wants chunking first. |
| D41 | Auto-sync **skips accounts dormant past `AUTO_SYNC_DORMANT_DAYS` (14)**; liveness tracked via `users.last_seen_at`, written on its own session | active | 2026-07-28. `auto_sync_tick` looped every non-deleted user, so an account that signed up once and never returned kept costing Claude calls hourly forever — the cost that scales with churn instead of usage, and the one that gets worse the more people try the app and drift away. `last_seen_at` is NOT NULL with `server_default now()`, so existing rows backfill to "seen at deploy" (current testers are never wrongly skipped) and a brand-new user is eligible for their first sync immediately. Skipping is a pause, not a tombstone: one authenticated request re-arms the account on the next tick, and because the scan window is 30 days a returning user catches up on anything still in-window. **The liveness write deliberately opens its OWN session.** The first cut wrote on the request's session and rolled back on failure — and `rollback()` expires every loaded attribute, including the `user` the auth dependency is about to return, so the endpoint's next plain `user.id` raised `MissingGreenlet`. That turned a transient DB blip into a guaranteed 500 across all authenticated traffic, precisely when the DB was already struggling — the exact opposite of the comment's claim that it could never fail a request. Found by the security audit; verified (all 8 columns expired, sync access raises). A separate session also avoids a second issue: committing on the shared session would sweep in whatever a later-added dependency had staged. Write is throttled to one per hour (it runs on every authenticated request). **Known gap, PM decision not a code fix:** a user whose only interaction is *reading* push reminders without ever opening the app would go dormant at 14 days; opening the app from a notification re-arms it, and `AUTO_SYNC_DORMANT_DAYS=0` disables the skip entirely. |

| D43 | Android OAuth redirect is delivered to **MainActivity via app_links with PKCE persisted to Keystore**, not via flutter_web_auth_2's CallbackActivity; **iOS keeps the plugin** | active | 2026-07-28. Long-standing bug: after completing Google consent, Android users were never returned to the app. Root cause confirmed on the PM's own S25 Ultra rather than inferred — `CallbackActivity` does `FlutterWebAuth2Plugin.callbacks.remove(scheme)?.success(url)` then `finishAndRemoveTask()`, and `callbacks` is a **static in-process map**. While the user is on the consent screen the app is backgrounded and Android may kill it (routine here: the app sits in the **RARE standby bucket**); the redirect then cold-starts the process, the map is empty, `?.success` is a silent no-op, and `finishAndRemoveTask()` wipes the task. Reproduced with the process dead: `CallbackActivity` cold-started, was destroyed, and `topResumedActivity` became the Samsung launcher — MainActivity never ran. After the fix the identical test lands on `.MainActivity`, no crash, `CallbackActivity` absent entirely. Fix: (a) the redirect intent-filter moves to MainActivity (`singleTask`) and the plugin's CallbackActivity declaration is removed on Android; (b) the PKCE **verifier + state are persisted before the browser opens** — they were local variables that died with the process, and they are the only values that cannot be reconstructed afterwards; (c) `app_links` delivers the redirect including the cold-start initial link; (d) `recoverPendingAuthorization()` completes an interrupted sign-in at startup, keeping the RFC 8252 `state` check so persistence does not weaken callback binding, and consuming the record so a code cannot be replayed. **iOS deliberately untouched** — `ASWebAuthenticationSession` returns the URL directly in-process and has never had this failure mode, so changing it would be pure risk. Startup recovery never throws: a user merely opening the app must not be blocked by a stale record. **Supersedes the earlier R8/ProGuard hypothesis**, which was wrong — the first `resolve-activity` check used the wrong package name (`com.bettersaas.mamaflow` rather than `com.bettersaas.mamaflow.mamaflow`), so that evidence was worthless; re-checked correctly, the activity resolved fine all along. **Not yet proven end-to-end**: the structural half is verified on-device and the recovery logic is unit-tested, but a full real-consent → kill → recover run still needs a human. |

| D45 | **`mail_connections`**: a user may connect several mailboxes; sync runs over all of them with a **shared** per-run cap; adding a mailbox is an authenticated action distinct from sign-in | active | 2026-07-30. Step 2 of D44 — the capability the caps are a policy over. Implements the table deferred at D38, where Phase 1 kept one mail source per user and every sign-in purged the other provider's credential, making a second mailbox impossible and leaving pro/family with nothing to sell. `email` on the connection is the MAILBOX address, not the sign-in identity (the point of the table), and doubles as the credential-store key — tokens were already keyed by (email, provider), so each connection maps to its own secret with no key changes. Partial unique index on live rows only, so disconnect+reconnect revives rather than colliding with the tombstone. **The migration's backfill is load-bearing**: sync reads mailboxes from this table, so without it every existing user silently stops syncing; verified on real Postgres 16 (backfill excludes soft-deleted users, duplicate live mailbox rejected, reconnect permitted, downgrade clean). **Cost:** the per-run message cap is shared ACROSS mailboxes, not applied per mailbox — per mailbox it would multiply per-tick Claude spend by the mailbox count, the same runaway shape as D39. Dedup and the daily budget were already per user, so mail arriving in two mailboxes is extracted once. **Resilience:** `ReauthRequired` is per mailbox, so one revoked app password no longer stops the others; the run only fails as "please sign in" when every mailbox is broken. **API:** `POST /account/mailboxes` (authenticated — adding a mailbox must be distinguishable from creating a second account) checks the cap *before* any IMAP round trip so we never make the user wait on, or briefly hold a credential for, a request we are about to reject; `DELETE /account/mailboxes/{id}` destroys the credential then the row and is user-scoped so an id alone cannot disconnect someone else's mailbox. **Two security holes found and closed while wiring this:** (1) account deletion purged only the IDENTITY email's credentials, so other mailboxes' app passwords would have survived deletion — now every connection is revoked and purged, read before the rows are soft-deleted so they cannot become unreachable; (2) removing purge-on-switch could have resurrected the D38 stale-app-password hole, so `ensure_connection` purges other providers for the MAILBOX being connected, unconditionally — a row-based check would miss a credential that has no row behind it. Auto-sync eligibility became "has a connected mailbox" rather than "the identity address has a credential", which had skipped users whose mailboxes are all other addresses. **Audit (2026-07-30) found four BLOCKs, all fixed:** (a) the shared IMAP helper was infinitely self-recursive so `POST /account/mailboxes` 500'd on every real call — and the suite stayed green because every test of it mocked that exact function, so the replacement tests drive the real router and are proven non-vacuous; (b) credentials were purged BEFORE the cap check, so a rejected 402 had already destroyed a live credential, possibly another account's — the purge now runs only once the connection is established; (c) two accounts could connect the same address, and because the credential store is keyed globally by (email, provider) with no user in the key, the second silently overwrote the first's secret while either disconnecting destroyed it for both, leaving the loser a mailbox that still showed connected, still occupied a cap slot and could never sync — now refused (409) and enforced by a partial unique index on **email alone** rather than (user_id, email), which also removes the race; (d) `delete_account`'s per-connection token calls were unguarded and ran AFTER the soft-delete commit, so one transient Secret Manager fault abandoned the loop and left the remaining secrets alive with their rows already deleted and therefore unreachable forever — credentials are now purged BEFORE the rows are marked, each mailbox isolated, and a connection whose purge fails is left live so it stays discoverable.
